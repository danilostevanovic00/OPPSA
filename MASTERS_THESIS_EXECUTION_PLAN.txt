MASTER'S THESIS EXECUTION PLAN
TOPIC: RELIABILITY AND FAULT TOLERANCE OF A MICROSERVICE-BASED WMS

PURPOSE OF THIS FILE
This file turns the thesis idea into an actual execution plan for THIS project.
It assumes:
  - you keep the existing 3-service WMS as the experimental system
  - you do NOT add new business features, new public APIs, or new business RabbitMQ flows
  - you focus only on reliability, fault tolerance, observability, deployment, and experiments
  - you want a scope that is realistic for a 50-60 page Master's thesis

IMPORTANT DECISION ABOUT OBSERVABILITY
Yes, you can use Spring Boot Actuator and NOT use Prometheus, Grafana, Loki, or ELK.
That is acceptable for a Master's thesis IF you are disciplined about collecting and saving data.

For this thesis, a sufficient lightweight measurement stack is:
  1. Spring Boot Actuator endpoints from each service
  2. application logs from each service
  3. RabbitMQ Management UI / HTTP API data
  4. kubectl events, pod status, restart counts, and logs
  5. simple CSV or TXT files where you manually store each experiment run's results

You do NOT need a full monitoring platform unless your mentor explicitly asks for one.

0. WHAT YOU ARE ACTUALLY TRYING TO PROVE
====================================================================

This thesis should NOT say:
  "I added Kubernetes and some resilience libraries to my WMS."

It SHOULD say:
  "I experimentally evaluated how selected reliability and fault-tolerance
   mechanisms affect availability, message reliability, latency, and recovery
   behavior in an existing RabbitMQ-based Spring Boot microservice WMS."

That means every technical change must exist for one of these reasons:
  - to create a baseline
  - to inject a fault
  - to collect measurements
  - to compare baseline vs improved configuration

====================================================================

Do ONLY these 3 experiment groups.

EXPERIMENT GROUP 1: Kubernetes recovery and replication
Question:
  How do replication and Kubernetes recovery mechanisms affect service
  availability and recovery time when a microservice crashes?

Mechanisms:
  - Kubernetes Deployments
  - 1 replica vs 3 replicas
  - liveness probe
  - readiness probe

Fault:
  - deliberately kill one service pod during workload

Question:
  How do acknowledgement strategy, retry handling, dead-letter handling,
  and idempotent consumption affect message reliability when a consumer fails?

Mechanisms:
  - acknowledgement control
  - retry behavior
  - dead-letter queue
  - idempotent processing

Fault:
  - make a consumer fail during message processing


EXPERIMENT GROUP 3: Slow or unstable dependency behavior
Question:
  How do timeout, retry, and circuit breaker mechanisms affect latency,
  success rate, and system stability under degraded conditions?

Mechanisms:
  - timeout
  - retry
  - circuit breaker

Fault:
  - artificial delay or temporary downstream unavailability

11. EXPERIMENT GROUP 1 - KUBERNETES RECOVERY AND REPLICATION
====================================================================

EXPERIMENT 1A - SINGLE REPLICA CRASH
Purpose:
  Establish how visible a service crash is when only one replica exists.

Configuration:
  - 1 replica for the chosen service
  - readiness and liveness probes enabled

Fault:
  - kill the pod of one service during active workload

Best service to target first:
  - orders-service
Reason:
  - it orchestrates the central workflow and has both REST and messaging importance

Workload:
  - continuously send create-order and confirm-order requests
  - optionally complete payment for a subset of them

Metrics:
  - failure detection time
  - pod restart time
  - readiness recovery time
  - failed request count during outage
  - request latency around the crash window

What to observe:
  - how long clients see errors
  - whether in-flight requests fail
  - how fast Kubernetes replaces and readies the pod


EXPERIMENT 1B - MULTI-REPLICA CRASH
Purpose:
  Compare 1 replica vs 3 replicas under the same crash scenario.

Configuration:
  - 3 replicas for the same service
  - same probes
  - same workload

Fault:
  - kill 1 pod during workload

Main comparison:
  - visible downtime with 1 replica vs visible downtime with 3 replicas
  - latency spikes with 1 replica vs 3 replicas
  - error rate with 1 replica vs 3 replicas
  - resource cost difference

Expected conclusion direction:
  Replication should improve availability but use more resources.


HOW TO RUN THIS EXPERIMENT IN PRACTICE
  1. Deploy with replicas=1.
  2. Start workload.
  3. Record current time.
  4. Delete the selected pod.
  5. Record:
       - first visible failure time
       - new pod start time
       - readiness time
       - return-to-normal time
  6. Repeat 5-10 times.
  7. Deploy with replicas=3.
  8. Repeat the exact same steps.

WHAT TO SAVE FOR EACH RUN
  - kubectl get pods output before fault
  - kubectl describe pod output after restart
  - kubectl get events output
  - service logs around the crash window
  - workload results
  - actuator metrics snapshot before/during/after fault

12. EXPERIMENT GROUP 2 - RABBITMQ CONSUMER RELIABILITY
====================================================================

THIS IS PROBABLY THE MOST IMPORTANT THESIS EXPERIMENT.

MAIN IDEA
You want to study what happens when a consumer receives a message but fails
before the processing is safely completed.

BASELINE VERSION
  - current behavior as close as possible to the existing project

IMPROVED VERSION
  - acknowledgement strategy chosen deliberately
  - retry handling
  - dead-letter queue for poison or repeatedly failing messages
  - idempotent consumption where needed

CRITICAL FAILURE POINTS TO TEST
Choose 1 or 2, not all of them.

Recommended failure point A:
  - consumer receives message
  - processing starts
  - service crashes before completion

Recommended failure point B:
  - database write happens
  - failure occurs before acknowledgement or before follow-up completion

WHY THESE FAILURE POINTS MATTER
They reveal whether your system risks:
  - lost messages
  - duplicated processing
  - inconsistent business state


EXPERIMENT 2A - BASELINE CONSUMER FAILURE
Target suggestion:
  - inventory-service consumer for stock reservation
or
  - orders-service consumer handling downstream events

Fault:
  - inject a controlled failure during message handling

What to measure:
  - was the message redelivered
  - was the business effect lost
  - was the business effect duplicated
  - what happened to queue depth
  - how long until final completion, if any


EXPERIMENT 2B - IMPROVED CONSUMER RELIABILITY
Mechanisms to introduce:
  - manual acknowledgement or controlled acknowledgement behavior
  - retry attempts with clear limits
  - dead-letter queue for repeated failure
  - idempotency guard at the consumer/business boundary

What to compare against baseline:
  - lost messages
  - duplicate operations
  - successful eventual completion
  - redelivery count
  - queue buildup
  - consistency of final database state


HOW TO RUN THIS EXPERIMENT IN PRACTICE
  1. Trigger a workflow that publishes the chosen message.
  2. Confirm the message reaches the target queue.
  3. Force the consumer to fail at the selected point.
  4. Observe RabbitMQ queue state and redelivery behavior.
  5. Observe resulting database state.
  6. Repeat for the baseline configuration.
  7. Add the improved reliability mechanism(s).
  8. Repeat the exact same fault scenario.
  9. Compare final message and business outcomes.

WHAT TO SAVE FOR EACH RUN
  - queue ready count
  - queue unacked count
  - redelivery observations
  - dead-letter queue state, if used
  - logs from producer and consumer
  - final DB state for the affected business records

IMPORTANT BUSINESS CORRECTNESS CHECKS
Depending on the chosen message flow, verify:
  - stock was not reserved twice
  - invoice was not created twice
  - payment effect was not applied twice
  - shipment request state remained consistent

13. EXPERIMENT GROUP 3 - SLOW OR UNSTABLE DEPENDENCY BEHAVIOR
====================================================================

PURPOSE
Study trade-offs between better resilience and worse latency / extra work.

BEST PRACTICAL INTERPRETATION FOR THIS PROJECT
Introduce delay or temporary unavailability around one service interaction
path and compare behavior with and without timeout/retry/circuit breaker.

IMPORTANT NOTE
Because your system is largely message-driven, this experiment does not need
to look exactly like a classic synchronous REST chain. You only need one clear,
controlled degraded path and a valid measurement strategy.

SIMPLEST USEFUL VERSION
  - choose one service interaction or one external dependency path
  - inject delay
  - measure how requests and processing times change
  - add timeout/retry/circuit breaker
  - measure again


EXPERIMENT 3A - DEGRADED BASELINE
Fault:
  - artificial delay or temporary unavailability in the chosen path

Metrics:
  - request latency
  - timeout/failure count
  - throughput
  - backlog growth if messages accumulate


EXPERIMENT 3B - RESILIENCE-ENHANCED VERSION
Mechanisms:
  - timeout
  - bounded retry
  - circuit breaker

Compare:
  - success rate
  - p95 or p99 latency if possible
  - throughput
  - amount of extra retry traffic
  - whether the system fails fast instead of hanging

EXPECTED THESIS VALUE
This experiment gives you the trade-off discussion:
  - resilience can improve stability
  - but it may increase latency, complexity, and sometimes resource usage
