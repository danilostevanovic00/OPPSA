====================================================================
ORDERS-SERVICE — FULL BEGINNER EXPLANATION OF EVERY FILE AND ANNOTATION
====================================================================

This file explains, in plain language, every class and every annotation
used in orders-service, so you can learn what Spring Boot / JPA /
Hibernate / RabbitMQ are actually doing under the hood.

Orders-service's job (per the project spec, "Modul Porudzbine i
Isporuke"): accept customer orders, calculate selling prices, run the
SAGA PATTERN that coordinates with inventory-service to reserve stock,
handle payment confirmations from billing-service, create invoices, and
run a daily scheduled job to expire unpaid orders.

Read BILLING_SERVICE_EXPLAINED.txt first (basic Spring/JPA concepts) and
ideally INVENTORY_SERVICE_EXPLAINED.txt second (relationships, RabbitMQ
publish/consume basics) - this file assumes you already know those and
focuses on what's NEW here: the SAGA PATTERN and the SCHEDULED JOB.


====================================================================
1. THE OVERALL SHAPE OF THIS SERVICE (LAYERED ARCHITECTURE)
====================================================================

    controller/   -> OrderController.java                   (1 file)
    service/      -> OrderService.java                       (1 file, the biggest file in the whole project)
    repository/   -> 4 repository interfaces
    entity/       -> 9 JPA entities/enums
    dto/          -> 5 REST request/response DTOs
    messaging/    -> 7 message DTOs + OrdersPublisher + OrdersConsumer
    config/       -> RabbitMQConfig.java
    (root)        -> OrdersServiceApplication.java

Total: 31 files. This service owns its OWN separate PostgreSQL database
(completely isolated from inventory-service's and billing-service's
databases) - even though it deals with "items" and "prices", it keeps
its own LOCAL COPY of whatever data it needs (synced via RabbitMQ
events), rather than ever querying inventory-service's database directly.


====================================================================
2. OrdersServiceApplication.java  (entry point)
====================================================================

@SpringBootApplication
@EnableScheduling
public class OrdersServiceApplication {
    public static void main(String[] args) {
        SpringApplication.run(OrdersServiceApplication.class, args);
    }
}

Same role as the other two services' main classes, PLUS one new
annotation:

ANNOTATION: @EnableScheduling
  This is REQUIRED for the @Scheduled annotation (used later in
  OrderService's daily expiry job) to actually take effect. Without
  @EnableScheduling here, Spring would completely IGNORE any @Scheduled
  method anywhere in the application - it wouldn't error, it just
  silently wouldn't run. Neither billing-service nor inventory-service
  has any scheduled jobs, so neither needs this annotation.

3. ENTITIES (entity/ folder) — 9 files
====================================================================

--------------------------------------------------------------------
3.1 Order.java
--------------------------------------------------------------------
// "order" is a reserved SQL word; use customer_orders to avoid conflicts
@Entity
@Table(name = "customer_orders")
public class Order {
    @Id
    @Column(name = "id", length = 50)
    private String id;   // a UUID string, NOT auto-generated by the database

    private LocalDate creationDate;
    private String customerCode;
    private String customerName;
    private String deliveryAddress;

    @Enumerated(EnumType.STRING)
    private OrderStatus status = OrderStatus.CREATED;

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL,
               orphanRemoval = true, fetch = FetchType.EAGER)
    private List<OrderItem> items = new ArrayList<>();
}

- The customer's order ("porudzbina" in the spec). Lives ENTIRELY inside
  orders-service's own database - it never touches inventory-service's
  database directly. This is the core rule of microservices: each
  service owns its data exclusively.
- @Table(name = "customer_orders"): notice the table is explicitly named
  something OTHER than "order", because "ORDER" is a reserved keyword in
  SQL (part of "ORDER BY") - using it as a literal table name would
  cause confusing errors, so it's renamed.
- The @Id here is a String UUID (like
  "a1b2c3d4-e5f6-...") generated in the SERVICE LAYER via
  UUID.randomUUID().toString() - NOT auto-generated by the database like
  most other entities. This is needed because this id gets passed AROUND
  BETWEEN MICROSERVICES inside RabbitMQ messages later (as the orderId,
  and then the derived shipmentRequestId) - a UUID is guaranteed globally
  unique without any central database counter coordinating between services.
- fetch = FetchType.EAGER (different from most other @OneToMany in this
  whole project, which use LAZY!): the items list is loaded from the
  database IMMEDIATELY alongside the Order itself. This was chosen
  because the service layer almost always needs the order's items right
  away (e.g. to calculate totals) - using LAZY here would just cause an
  extra round-trip database query almost every single time anyway.

--------------------------------------------------------------------
3.2 OrderItem.java
--------------------------------------------------------------------
One line of an Order (the "detail" side of the header/detail pair).

    private BigDecimal sellingPricePerUnit;

- sellingPricePerUnit is CALCULATED and PERMANENTLY STORED here at
  order-creation time (avgPurchasePrice * (1 + margin)) - this is
  sometimes called a "price snapshot". Reasoning: if the item's margin
  setting changes LATER (via setCustomMargin), past orders should keep
  showing the price the customer actually agreed to at the time, not
  silently change retroactively.

--------------------------------------------------------------------
3.3 ItemPricing.java
--------------------------------------------------------------------
// Local copy of item data synced from Inventory via events; stores running average purchase price
@Entity
@Table(name = "item_pricing")
public class ItemPricing {
    @Id private String itemCode;
    private String itemName;
    private String unitOfMeasure;
    private BigDecimal averagePurchasePrice;
    private BigDecimal customMarginPercent;   // null means use the default 15%
    private BigDecimal totalQuantityReceived = BigDecimal.ZERO;
    private LocalDateTime lastUpdated;
}

- THIS is orders-service's LOCAL CACHE of item data it needs, kept in
  sync purely via RabbitMQ events from inventory-service (ItemCreated,
  StockReplenished) - orders-service NEVER queries inventory-service's
  database directly; the two databases are completely separate and
  isolated (see docker-compose.yml: postgres-orders vs postgres-inventory
  are two entirely different PostgreSQL containers).
- This is the standard microservices trade-off: you duplicate a small
  amount of data locally, in exchange for services not being tightly
  coupled to each other's databases or uptime (if inventory-service's
  database goes down, orders-service can still calculate prices using
  its last-known cached values).
- averagePurchasePrice is recalculated every time a StockReplenished
  event arrives, using a WEIGHTED AVERAGE formula (explained in detail
  in section 9 below) so a single unusually cheap or expensive delivery
  doesn't distort the whole price history.

--------------------------------------------------------------------
3.4 OrderStatus.java  and  3.5 ShipmentRequestStatus.java  (enums)
--------------------------------------------------------------------
public enum OrderStatus {
    CREATED, CONFIRMED, CANCELLED
}

public enum ShipmentRequestStatus {
    PENDING,          // waiting for stock reservation
    PAYMENT_READY,    // stock reserved, waiting for payment
    COMPLETED,        // payment confirmed, invoice created
    CANCELLED,        // stock reservation failed (Saga compensation)
    EXPIRED           // payment deadline passed
}

- OrderStatus is a simple lifecycle: created by the customer, then
  confirmed (which TRIGGERS the whole Saga), or cancelled.
- ShipmentRequestStatus IS LITERALLY THE SAGA'S STATE MACHINE - every
  single event handler method in OrderService just moves this one status
  field forward (or sideways into CANCELLED/EXPIRED) as replies arrive
  asynchronously from other services. Understanding this one enum is
  basically understanding the whole Saga.

--------------------------------------------------------------------
3.6 ShipmentRequest.java  — THE CENTRAL ENTITY OF THE WHOLE SAGA PATTERN
--------------------------------------------------------------------
@Entity
@Table(name = "shipment_requests")
public class ShipmentRequest {
    @Id private String id;              // another UUID, generated at confirmOrder() time

    @ManyToOne private Order order;
    private BigDecimal totalAmount;
    private LocalDate paymentDeadline;

    @Enumerated(EnumType.STRING)
    private ShipmentRequestStatus status = ShipmentRequestStatus.PENDING;

    @OneToMany(mappedBy = "shipmentRequest", cascade = CascadeType.ALL,
               orphanRemoval = true, fetch = FetchType.EAGER)
    private List<ShipmentRequestItem> items = new ArrayList<>();

    @OneToOne(mappedBy = "shipmentRequest", cascade = CascadeType.ALL)
    private Invoice invoice;
}

- Created the MOMENT confirmOrder() runs - BEFORE inventory-service has
  even replied about whether the stock is actually available! This is
  the defining trait of the Saga pattern: you optimistically create your
  own local record first, then react to whatever the other
  service/database says afterward (since you can't wrap two separate
  databases in one atomic all-or-nothing commit).
- @OneToOne(mappedBy = "shipmentRequest"): a NEW relationship type not
  seen in inventory-service. Means "exactly one ShipmentRequest links to
  at most one Invoice". mappedBy again means this is the NON-owning
  side - Invoice is the class that actually holds the foreign key
  column. This field stays NULL until handlePaymentConfirmed() (in
  OrderService) creates and attaches an Invoice much later.

--------------------------------------------------------------------
3.7 ShipmentRequestItem.java
--------------------------------------------------------------------
A line-item SNAPSHOT copied from OrderItem at confirmOrder() time - kept
as entirely separate rows (rather than just reusing the original
OrderItem rows) so the Saga has a stable, independent copy that won't
change even if the original Order/OrderItem were somehow modified later.

--------------------------------------------------------------------
3.8 Invoice.java  and  3.9 InvoiceItem.java
--------------------------------------------------------------------
The "fatura" from the spec - created ONLY ONCE, inside
handlePaymentConfirmed() (see section 9 below), never before. Invoice is
the OWNING side of the one-to-one relationship with ShipmentRequest (it
holds the actual shipment_request_id foreign-key column). InvoiceItem
mirrors ShipmentRequestItem but additionally pre-computes and stores
totalPrice (quantity * unitPrice) so it never needs recalculating later
just to display an invoice.

4. REPOSITORIES (repository/ folder) — 4 files
====================================================================

Same JpaRepository pattern as the other two services. One NEW kind of
derived query method appears here:

ShipmentRequestRepository:
    List<ShipmentRequest> findByStatusAndPaymentDeadlineBefore(
            ShipmentRequestStatus status, LocalDate date);

- Parsed by Spring Data JPA as "find ... By Status And PaymentDeadline Before":
      SELECT * FROM shipment_requests
      WHERE status = ? AND payment_deadline < ?
- This single method is what POWERS the entire daily scheduled expiry
  job (explained in section 9.7 below) - it finds every ShipmentRequest
  that's still waiting for payment (PAYMENT_READY) but whose deadline
  has already passed.

The other 3 repositories (OrderRepository, ItemPricingRepository,
InvoiceRepository) are plain JpaRepository<Entity, IdType> interfaces
with no extra custom methods needed.

5. DTOs (dto/ folder) — 5 files
====================================================================

CreateOrderRequest / CreateOrderItemRequest
  Body for POST /api/orders. Notice these do NOT include any price
  fields at all - prices are ALWAYS calculated server-side from
  ItemPricing. This is an important security/correctness principle:
  never trust a client to tell you what something costs.

OrderResponse / OrderItemResponse
  What createOrder() returns. "status" is exposed as a plain String
  (e.g. "CREATED"), not the raw OrderStatus enum object - this is
  conventional for REST APIs, since a plain string like "CREATED" is
  much simpler JSON than something like {"name": "CREATED"}. The
  conversion `order.getStatus().name()` does exactly this: turns an enum
  constant into its String form.

ShipmentRequestResponse
  What confirmOrder() returns - lets the caller know the Saga has
  STARTED. Its "status" field will usually still say "PENDING" at this
  EXACT moment, since inventory-service's reply always arrives a little
  later, asynchronously (watch the [SAGA] log lines in the Docker
  console to see it progress from PENDING to PAYMENT_READY in real time).

6. MESSAGING (messaging/ folder) — 9 message classes + Publisher + Consumer
====================================================================

--------------------------------------------------------------------
6.1 The 9 message DTO classes
--------------------------------------------------------------------

RECEIVED from inventory-service (orders-service is the listener):
  ItemCreatedEvent          - triggers local catalog sync
  StockReplenishedEvent     - triggers purchase price recalculation
  StockReservedEvent        - Saga success reply (has nested ReservationDetail)
  StockReservationFailedEvent - Saga failure reply, triggers compensation

SENT to inventory-service (orders-service is the sender):
  ReserveStockMessage       - Saga step 1, "please reserve this stock" (has nested StockItem)
  CancelReservationMessage  - "please release this reservation" (used by the scheduled job)
  GoodsSoldMessage          - final step, "the payment is confirmed, remove the stock for good" (has nested SoldItem)

RECEIVED from billing-service:
  PaymentConfirmedMessage   - triggers Invoice creation + sending GoodsSoldMessage

SENT to billing-service (NEW - added to keep Billing's local
"payment-readiness" cache in sync, see repo memory notes / the
billing-service explanation file for the full design rationale):
  ShipmentPaymentReadyEvent          - "this shipment just became payable"
                                        (published from handleStockReserved,
                                        right after status -> PAYMENT_READY)
  ShipmentPaymentReadyCancelledEvent - "this shipment stopped being payable"
                                        (published from
                                        cancelExpiredShipmentRequests, right
                                        after status -> EXPIRED - without
                                        this, Billing's cache would go stale
                                        and could accept a late payment for
                                        something Orders already gave up on)
  Unlike the other message classes above, orders-service is the SENDER for
  both of these (billing-service is the listener) - so THESE two classes
  (in orders-service's messaging/ package) DO need an explicit constructor
  taking shipmentRequestId, since OrdersPublisher constructs them directly
  before sending. Billing-service's own separate copies of these two
  classes have no explicit constructors at all (they only ever
  deserialize them, never construct/send one).

All of these follow the exact same "field names must match the OTHER
service's own separate copy of the same class exactly" rule explained in
inventory-service's messaging section - there's no shared code between
any of the three microservices' Maven projects.

--------------------------------------------------------------------
6.2 OrdersPublisher.java
--------------------------------------------------------------------
Same pattern as InventoryPublisher/BillingPublisher - the ONE class that
sends messages, using RabbitTemplate. FIVE publish methods now (up from
three): publishReserveStock, publishCancelReservation, publishGoodsSold
(all three to inventory-service), plus the two NEW ones -
publishShipmentPaymentReady and publishShipmentPaymentReadyCancelled
(both to billing-service).

--------------------------------------------------------------------
6.3 OrdersConsumer.java
--------------------------------------------------------------------
This class receives EVERYTHING orders-service listens to - the most
"connected" consumer of all 3 services:
  @RabbitListener(queues = Q_ITEM_CREATED)             -> handleItemCreated
  @RabbitListener(queues = Q_STOCK_REPLENISHED)        -> handleStockReplenished
  @RabbitListener(queues = Q_STOCK_RESERVED)           -> handleStockReserved       (Saga success)
  @RabbitListener(queues = Q_STOCK_RESERVATION_FAILED) -> handleStockReservationFailed (Saga failure)
  @RabbitListener(queues = Q_PAYMENT_CONFIRMED)        -> handlePaymentConfirmed

Note: OrdersConsumer itself did NOT gain any new @RabbitListener methods
for the two new events above - that makes sense, because orders-service
is the SENDER of ShipmentPaymentReadyEvent/Cancelled, not the receiver.
It's billing-service's NEW BillingConsumer class that listens for those
two (see the billing-service explanation file, section 13).

Every method just immediately delegates to the matching method in
OrderService - no business logic lives in this class itself.

7. config/RabbitMQConfig.java
====================================================================

Structurally identical to inventory-service's RabbitMQConfig (same
EXCHANGE name "wms.topic.exchange" shared across ALL THREE services, same
Queue/Binding/Jackson2JsonMessageConverter/RabbitTemplate/
SimpleRabbitListenerContainerFactory beans) - just with the routing
keys/queues REVERSED in direction: here, orders-service PUBLISHES what
inventory-service AND billing-service listen for (RK_RESERVE_STOCK,
RK_CANCEL_RESERVATION, RK_GOODS_SOLD to Inventory; RK_SHIPMENT_PAYMENT_READY
and RK_SHIPMENT_PAYMENT_READY_CANCELLED to Billing - these two are NEW),
and CONSUMES what inventory-service/billing-service publish
(RK_ITEM_CREATED, RK_STOCK_REPLENISHED, RK_STOCK_RESERVED,
RK_STOCK_RESERVATION_FAILED, RK_PAYMENT_CONFIRMED).

IMPORTANT: since orders-service is the PUBLISHER (not the listener) for
RK_SHIPMENT_PAYMENT_READY/RK_SHIPMENT_PAYMENT_READY_CANCELLED, this
service's OWN RabbitMQConfig does NOT need to declare a Queue or Binding
for them - only the two routing key String constants (so
OrdersPublisher's convertAndSend calls have something to reference). The
actual Queue + Binding for these two live entirely in BILLING-SERVICE's
RabbitMQConfig instead, since billing-service is the one that needs
somewhere for those messages to land and wait to be consumed.

One small style difference worth noting - 5 of the Queue @Bean methods
are written compactly on one line each:
    @Bean public Queue itemCreatedQueue() { return new Queue(Q_ITEM_CREATED, true); }
This is functionally 100% identical to the multi-line style used
elsewhere - just a formatting choice since there are 5 very similar
queues to declare here.

8. controller/OrderController.java  (REST LAYER)
====================================================================

@RestController
@RequestMapping("/api/orders")
public class OrderController {

    @PostMapping
    public ResponseEntity<OrderResponse> createOrder(@RequestBody CreateOrderRequest request) { ... }

    @PostMapping("/{orderId}/confirm")
    public ResponseEntity<ShipmentRequestResponse> confirmOrder(@PathVariable String orderId) { ... }

    @PutMapping("/pricing/{itemCode}/margin")
    public ResponseEntity<Void> setCustomMargin(
            @PathVariable String itemCode,
            @RequestBody Map<String, BigDecimal> body) { ... }
}

- Same "thin controller" pattern as the other two services.
- @PostMapping (no path argument) on createOrder(): when @RequestMapping
  already set the class-level prefix to "/api/orders", an @PostMapping
  with NO extra path string means this method handles requests to that
  exact base path, i.e. POST /api/orders.
- confirmOrder needs no @RequestBody at all - the {orderId} URL path
  variable is the only input it needs.
- setCustomMargin combines BOTH @PathVariable (itemCode from the URL)
  AND @RequestBody (a Map<String, BigDecimal> parsed from the JSON body,
  e.g. {"marginPercent": 20}) in the same method - perfectly valid, a
  method can use as many different parameter-binding annotations as it needs.
- @PutMapping: another HTTP verb annotation (like @PostMapping/@GetMapping),
  conventionally used for "update/replace an existing resource" operations.


====================================================================
9. service/OrderService.java  — THE MOST IMPORTANT CLASS IN THE PROJECT
====================================================================

This single class implements the ENTIRE Saga pattern orchestration, the
selling-price calculation, and the scheduled expiry job. It's worth
understanding thoroughly.

--------------------------------------------------------------------
WHAT IS "THE SAGA PATTERN", REALLY?
--------------------------------------------------------------------
A "Saga" is how you handle a multi-step transaction that spans SEVERAL
microservices/databases, where a normal single-database @Transactional
simply can't help you - inventory-service and orders-service each have
their own completely separate database, so there is NO WAY to wrap
changes to BOTH of them in one atomic all-or-nothing commit.

Instead, the Saga pattern works like this:
  1. Orders-service OPTIMISTICALLY creates a ShipmentRequest and asks
     Inventory (via a RabbitMQ message) to reserve stock.
  2. Inventory eventually replies (also via RabbitMQ) with either
     success or failure - this reply can arrive any amount of time
     later, since it travels over the network asynchronously.
  3. Orders-service REACTS to whichever reply arrives:
       - on SUCCESS, it moves the ShipmentRequest forward (PENDING -> PAYMENT_READY)
       - on FAILURE, it runs a "COMPENSATING TRANSACTION" - instead of
         undoing something in Inventory's database (which it CAN'T do
         directly), it undoes its OWN side of the process (marks its own
         ShipmentRequest as CANCELLED).

Every public method in OrderService is either:
  (a) STARTING a new Saga step (confirmOrder is the only one), or
  (b) REACTING to a reply that already happened elsewhere (all the
      handleXxx methods, invoked automatically by OrdersConsumer whenever
      a matching message arrives).

--------------------------------------------------------------------
9.1 createOrder(request)
--------------------------------------------------------------------
For each requested item:
  - looks up ItemPricing (or falls back gracefully to price ZERO if it's
    not synced locally yet - notice .orElse(null) here instead of
    .orElseThrow(), a deliberate choice to not fail the whole order just
    because pricing data hasn't arrived via RabbitMQ yet)
  - calls calculateSellingPrice(pricing) (see section 9.8 below) and
    stores the result permanently on the OrderItem
Then saves the whole Order (cascading saves every OrderItem too).

Note: UUID.randomUUID().toString() generates the Order's id - a
randomly generated string guaranteed (for all practical purposes) never
to collide with any other id, anywhere, without any central coordinator.

--------------------------------------------------------------------
9.2 confirmOrder(orderId)  — SAGA STEP 1: START
--------------------------------------------------------------------
- Validates the order exists and is still in CREATED status.
- Calculates the grand total using a JAVA STREAM:
      order.getItems().stream()
          .map(i -> i.getSellingPricePerUnit().multiply(i.getRequestedQuantity()))
          .reduce(BigDecimal.ZERO, BigDecimal::add)
  Explanation of Java Streams here: .stream() turns the List into a
  processing "pipeline". .map(...) transforms EACH OrderItem into its
  line total (price times quantity). .reduce(BigDecimal.ZERO, BigDecimal::add)
  sums every one of those line totals together into one final number,
  starting the running sum at zero. This whole expression is just a more
  compact, functional-programming-style replacement for writing a
  for-loop with a running total variable by hand.
- Creates the ShipmentRequest (see section 3.6 above) with status
  PENDING and a paymentDeadline of "today + paymentDeadlineDays" (an
  @Value-injected configuration setting, default 3 days).
- Copies every OrderItem into a matching ShipmentRequestItem snapshot.
- Saves everything, THEN builds and publishes a ReserveStockMessage -
  this is the literal moment the Saga "begins" from Inventory's
  perspective. Since this whole method is one @Transactional block, if
  publishReserveStock() somehow threw an exception, even the
  shipmentRequestRepository.save(sr) just before it would get rolled back too.

--------------------------------------------------------------------
9.3 setCustomMargin(itemCode, marginPercent)
--------------------------------------------------------------------
A simple "upsert" (update-or-insert): finds the existing ItemPricing row,
or creates a fresh blank one if none exists yet, then overwrites its
customMarginPercent field. Not explicitly named in the raw project spec
text, but required by the requirement "moguce je definisati posebnu
marzu po artiklu" (it's possible to define a special margin per item).

--------------------------------------------------------------------
9.4 handleStockReserved(event)  — SAGA STEP 2: SUCCESS PATH
--------------------------------------------------------------------
Called automatically (via OrdersConsumer) whenever inventory-service's
"it worked" reply arrives. Flips the matching ShipmentRequest's status
from PENDING to PAYMENT_READY, THEN (NEW) publishes a
ShipmentPaymentReadyEvent to billing-service:

    sr.setStatus(ShipmentRequestStatus.PAYMENT_READY);
    shipmentRequestRepository.save(sr);
    publisher.publishShipmentPaymentReady(new ShipmentPaymentReadyEvent(sr.getId()));

This publish is what keeps billing-service's LOCAL PaymentReadyShipment
cache in sync (see the billing-service explanation file, sections 5, 9,
11, 13) - without it, Billing would have no way to know this shipment is
now actually payable, short of directly querying orders-service's
database or making a synchronous REST call (both of which this design
deliberately avoids, to keep the two services loosely coupled).

--------------------------------------------------------------------
9.5 handleStockReservationFailed(event)  — SAGA STEP 2: FAILURE / COMPENSATION PATH
--------------------------------------------------------------------
shipmentRequestRepository.findById(event.getShipmentRequestId()).ifPresent(sr -> {
    sr.setStatus(ShipmentRequestStatus.CANCELLED);
    shipmentRequestRepository.save(sr);
});

- .ifPresent(lambda): a method on Java's Optional<T> type. The lambda
  code inside only runs IF the Optional actually contains a value - this
  is a null-safe alternative to writing "if (x != null) { ... }" by hand.
- THIS is literally the "compensating transaction" required by the
  project spec: since we have no way to reach into inventory-service's
  database and undo anything there, we instead undo the ONE thing WE
  ourselves already did (creating an optimistic ShipmentRequest) by
  marking it CANCELLED.

--------------------------------------------------------------------
9.6 handlePaymentConfirmed(message)  — THE FINAL STEP OF THE WHOLE BUSINESS FLOW
--------------------------------------------------------------------
Triggered by billing-service's PaymentConfirmed event (relayed through
OrdersConsumer). Validates the ShipmentRequest is actually in
PAYMENT_READY status (defensive check - refuses to process a payment for
something that was never actually reserved, or was already completed
once already), then:
  - flips status to COMPLETED
  - builds a brand-new Invoice, copying every ShipmentRequestItem into a
    matching InvoiceItem (pre-computing totalPrice for each line)
  - saves the invoice
  - builds and publishes a GoodsSoldMessage back to inventory-service -
    THIS is what finally triggers the physical removal of stock and
    DispatchNote creation over in inventory-service.

--------------------------------------------------------------------
9.7 cancelExpiredShipmentRequests()  — THE SCHEDULED JOB
--------------------------------------------------------------------
@Scheduled(cron = "${orders.expiry-check.cron:0 0 8 * * *}")
@Transactional
public void cancelExpiredShipmentRequests() {
    List<ShipmentRequest> expired = shipmentRequestRepository
            .findByStatusAndPaymentDeadlineBefore(ShipmentRequestStatus.PAYMENT_READY, LocalDate.now());

    for (ShipmentRequest sr : expired) {
        sr.setStatus(ShipmentRequestStatus.EXPIRED);
        shipmentRequestRepository.save(sr);
        publisher.publishCancelReservation(new CancelReservationMessage(sr.getId()));
        publisher.publishShipmentPaymentReadyCancelled(new ShipmentPaymentReadyCancelledEvent(sr.getId()));
    }
}

ANNOTATION: @Scheduled(cron = "...")
  Makes Spring run this method AUTOMATICALLY on a timer, completely in
  the background - no HTTP request, no incoming RabbitMQ message
  triggers it, it just fires by itself according to the schedule.
  Requires @EnableScheduling on the main Application class (see section
  2 above) to actually take effect at all.

CRON SYNTAX EXPLAINED:
  The pattern is "second minute hour day-of-month month day-of-week".
  The default value here, "0 0 8 * * *", means:
    second=0, minute=0, hour=8, day/month/weekday=* (any) ->
    "run at exactly 08:00:00, every single day".
  The "${orders.expiry-check.cron:0 0 8 * * *}" syntax is the same
  @Value-style property injection with a default value seen elsewhere -
  you could override just this one schedule via application.properties
  or an environment variable, without touching any code (handy for
  testing - e.g. temporarily setting it to run every minute).

WHAT THE JOB ACTUALLY DOES:
  Finds every ShipmentRequest still sitting in PAYMENT_READY status
  whose paymentDeadline has already passed (using the derived query
  method from section 4 above), marks each one EXPIRED, and sends TWO
  messages per expired ShipmentRequest:
    1. CancelReservationMessage to inventory-service - releases the
       reserved stock back to "available" (same cancelReservation()
       method used for the Saga failure path in inventory-service - it
       doesn't distinguish WHY the reservation is being cancelled, just
       that it should be).
    2. ShipmentPaymentReadyCancelledEvent to billing-service (NEW) -
       removes the corresponding row from Billing's local
       PaymentReadyShipment cache. WITHOUT this second message, Billing's
       cache would go stale/orphaned after expiry, and could still
       accept a late payment for a shipment that orders-service has
       already given up on and released the stock reservation for -
       which would then fail downstream in orders-service's own
       handlePaymentConfirmed() when it saw status=EXPIRED instead of
       PAYMENT_READY.

--------------------------------------------------------------------
9.8 handleItemCreated(event)  and  9.9 handleStockReplenished(event)
--------------------------------------------------------------------
These react to inventory-service's catalog-sync events, keeping the
local ItemPricing cache up to date.

handleItemCreated: an "upsert" that always overwrites itemName and
unitOfMeasure, even if a row already exists. Why "always", rather than
only on first insert? Because RabbitMQ gives NO GUARANTEE about ordering
between messages from DIFFERENT queues - a StockReplenished event could
technically arrive and create a "blank" ItemPricing row (with no name
yet) BEFORE the corresponding ItemCreated event is processed. Always
overwriting these two fields whenever ItemCreated does arrive guarantees
they eventually get filled in correctly regardless of arrival order.

handleStockReplenished: for each replenished item, calculates a NEW
weighted average purchase price:

    BigDecimal newAvg = oldAvg.multiply(oldQty)
            .add(repItem.getPurchasePrice().multiply(newQty))
            .divide(totalQty, 4, RoundingMode.HALF_UP);

WHAT IS A "WEIGHTED AVERAGE" AND WHY USE ONE HERE?
  Formula: (oldAvg * oldQty + newPrice * newQty) / (oldQty + newQty)
  Concrete example: you already had 100 units in stock at an average
  purchase price of 10.00. Now a new delivery brings 50 MORE units, but
  this time at 13.00 each. A NAIVE approach might just overwrite the
  price to 13.00 - but that would be wrong, since you still physically
  have 100 older, cheaper units sitting in the warehouse too. The
  weighted average instead gives you:
      (10.00*100 + 13.00*50) / 150 = 11.00
  The larger the existing quantity, the more it "pulls" the new average
  toward itself - exactly matching how real inventory accounting works.

--------------------------------------------------------------------
9.10 calculateSellingPrice(pricing)  — PRIVATE HELPER
--------------------------------------------------------------------
private BigDecimal calculateSellingPrice(ItemPricing pricing) {
    if (pricing == null || pricing.getAveragePurchasePrice() == null) {
        return BigDecimal.ZERO;
    }
    BigDecimal margin = pricing.getCustomMarginPercent() != null
            ? pricing.getCustomMarginPercent()
            : DEFAULT_MARGIN;   // DEFAULT_MARGIN = 15
    return pricing.getAveragePurchasePrice()
            .multiply(BigDecimal.ONE.add(margin.divide(BigDecimal.valueOf(100), 4, RoundingMode.HALF_UP)))
            .setScale(4, RoundingMode.HALF_UP);
}

Implements the project spec's core pricing rule EXACTLY: "selling price
= average purchase price * (1 + margin/100)", with a DEFAULT margin of
15% unless a custom per-item margin was explicitly set via
setCustomMargin(). "private" here means this method is an internal
implementation detail - not something any other class is meant to call
directly, only reused internally by createOrder() and logged inside
handleStockReplenished() to show what the new selling price would be.

9.11 toOrderResponse(order)  and  9.12 toShipmentRequestResponse(sr)  — MAPPER METHODS
--------------------------------------------------------------------
Both are "mapper" methods: they convert an internal @Entity object
(Order or ShipmentRequest) into the external-facing DTO that actually
gets serialized to JSON and sent back over REST. Keeping this conversion
logic in ONE place (rather than scattering entity-to-DTO logic all over
the controller or elsewhere) is a common, deliberate code organization
choice.

11. THE ENTIRE SAGA, END TO END, ACROSS ALL THREE SERVICES
====================================================================

1. Client:            POST /api/orders            -> createOrder()
2. Client:             POST /api/orders/{id}/confirm -> confirmOrder()
     - ShipmentRequest created, status = PENDING
     - publishes ReserveStockMessage ("stock.reserve")
3. (inventory-service) InventoryConsumer receives it, InventoryService.reserveStock() runs
     - SUCCESS -> publishes StockReservedEvent ("stock.reserved")
     - FAILURE -> publishes StockReservationFailedEvent ("stock.reservation.failed")
4. (orders-service) OrdersConsumer receives the reply:
     - handleStockReserved()          -> status = PAYMENT_READY, ALSO publishes
       ShipmentPaymentReadyEvent ("shipment.payment-ready") to billing-service (NEW)
     - handleStockReservationFailed() -> status = CANCELLED  (compensating transaction, Saga ends here on failure)
4.5. (billing-service, NEW) BillingConsumer receives ShipmentPaymentReadyEvent
     -> BillingService.markShipmentReadyForPayment() saves a row in the
        local PaymentReadyShipment cache - Billing now knows this shipment
        is payable, WITHOUT ever querying orders-service's database directly.
5. Client (assuming success):  POST /api/billing/pay  (a DIFFERENT microservice, billing-service)
     - BillingService.payShipment() FIRST checks the PaymentReadyShipment
       cache (NEW) - rejects the payment if no row exists for this
       shipmentRequestId (not reserved yet, already paid, or cancelled/expired)
     - if a row exists: saves a Payment row, DELETES the ready-cache row
       (this is what now prevents paying the same shipment twice),
       publishes PaymentConfirmedMessage ("payment.confirmed")
6. (orders-service) OrdersConsumer receives it -> handlePaymentConfirmed()
     - status = COMPLETED
     - Invoice created
     - publishes GoodsSoldMessage ("goods.sold")
7. (inventory-service) InventoryConsumer receives it -> InventoryService.processGoodsSold()
     - stock permanently reduced, DispatchNote created (status = READY_FOR_DISPATCH)

ALTERNATIVELY, if the customer never pays in time:
5'. Every day at 08:00, OrderService.cancelExpiredShipmentRequests() runs automatically
     - finds any ShipmentRequest still PAYMENT_READY past its deadline
     - marks it EXPIRED
     - publishes CancelReservationMessage ("reservation.cancel")
     - ALSO publishes ShipmentPaymentReadyCancelledEvent
       ("shipment.payment-ready-cancelled") to billing-service (NEW)
6'. (inventory-service) InventoryConsumer receives CancelReservationMessage
     -> InventoryService.cancelReservation()
     - the previously reserved stock is released back to "available"
6.5'. (billing-service, NEW) BillingConsumer receives
     ShipmentPaymentReadyCancelledEvent
     -> BillingService.removeShipmentReadyForPayment() deletes the
        corresponding row from the PaymentReadyShipment cache - closing
        the gap where a very late payment could otherwise still be
        accepted by Billing after Orders had already given up on the
        reservation.

That is the complete life of one order, coordinated ENTIRELY through
asynchronous RabbitMQ messages across three independent microservices,
each with its own separate database, with no direct database-to-database
connection between any of them anywhere in this project. The
payment-readiness cache in billing-service (steps 4.5, 5, and 6.5' above)
is the newest addition, closing a gap where Billing previously had no way
to know whether a shipment was actually ready to be paid for.

12. exception/  (NEW - GLOBAL EXCEPTION HANDLING LAYER)
====================================================================

Same three-file pattern as the other two services (full annotation
breakdown is in BILLING_SERVICE_EXPLAINED.txt, section 17):

    exception/ResourceNotFoundException.java  -> mapped to HTTP 404
    exception/ConflictException.java          -> mapped to HTTP 409
    exception/GlobalExceptionHandler.java     -> the @RestControllerAdvice

WHAT CHANGED IN OrderService.java:

    confirmOrder(orderId)               -> ResourceNotFoundException
      ("Order not found: ...")             if orderId doesn't exist -> 404
                                         -> ConflictException
      ("Order cannot be confirmed          if the order exists but is in the
        in status: ...")                   wrong status to confirm -> 409

    handleStockReserved(event)          -> ResourceNotFoundException
      ("ShipmentRequest not found: ...")

    handlePaymentConfirmed(message)     -> ResourceNotFoundException
      ("ShipmentRequest not found: ...")
                                         -> ConflictException
      ("ShipmentRequest not in              if payment arrives for a
        PAYMENT_READY status: ...")         shipment that's already
                                             COMPLETED/EXPIRED/CANCELLED -> 409

WHY BOTHER CHANGING handleStockReserved/handlePaymentConfirmed - THEY'RE
NOT CALLED FROM A CONTROLLER EITHER:
  Correct, both are only reached via OrdersConsumer (a @RabbitListener),
  same as inventory-service's saga methods - so GlobalExceptionHandler
  never actually intercepts these two specific throw sites. They were
  updated anyway purely for CONSISTENCY: every "this id doesn't exist"
  failure across the whole codebase now uses the same
  ResourceNotFoundException type and the same "not found" wording,
  making the RabbitMQ consumer logs (and future REST endpoints reusing
  these same service methods) predictable and uniform, instead of mixing
  IllegalArgumentException/IllegalStateException in some places and
  custom types in others.

WHY THIS MATTERS FOR THE SAGA SPECIFICALLY:
  createOrder() and confirmOrder() are the only two OrderService methods
  reachable directly from OrderController - so they're the only ones
  where a client sending a bad orderId or hitting confirm twice will
  now correctly get back HTTP 404 or 409 (with a clear "detail" message)
  instead of an opaque HTTP 500, without OrderController itself
  needing a single line of try/catch code.
